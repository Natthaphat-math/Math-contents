What happens when a signal gets it wrong?

Every time information travels — down a wire, through the air, across a disk — there's a chance something along the way flips a bit. Coding theory is the study of shaping information so a receiver can tell when that's happened, and sometimes even fix it.

This page follows that idea from a code that breaks silently, to one that can catch its own mistakes, to one that can correct them outright. Along the way you'll try each machine yourself.

A sender encodes a message into bits. A receiver only ever sees what arrives — never what happened on the way.

When one flipped bit changes everything

Say you're placing an order at a machine that only understands two-bit codes:

  • 00 — milk tea
  • 01 — tea
  • 10 — milk
  • 11 — coffee

If the sender wants milk tea, they send 00. But suppose the last digit gets flipped somewhere along the way, so 00 arrives as 01. The receiver has no reason to doubt it — 01 is a perfectly ordinary code. It gets decoded as tea, and the wrong order goes out, with nobody the wiser.

Notice that the receiver always sees a code that looks completely valid. There's no pattern here that only correct messages can produce, so there's no way to notice an error even exists.

Add a bit, gain a warning

The trouble with the two-bit code is that every possible pattern already means something. There's no room left to tell a correct code from a damaged one. So let's add a third bit, and only use four of the eight patterns it makes available:

  • 000 — milk tea
  • 011 — tea
  • 101 — milk
  • 110 — coffee

Now send milk, 101. If the middle digit flips, the receiver gets 111 — and 111 isn't assigned to anything. For the first time, the receiver knows something went wrong. They still can't be certain what was meant, since 111 is exactly one flip away from tea, milk, and coffee alike — but at least they know not to trust it.

This is the core trade-off in coding theory: detecting an error is easier than fixing one. Going further means designing codes with even more built-in redundancy — and a good place to watch that idea grow up is in how computers came to represent letters in the first place.

Counting the way early computers did: BCD

Long before computers handled full alphabets, they needed to handle decimal numbers reliably, for calculators, digital clocks, and accounting machines. Binary-coded decimal (BCD) does this by giving each decimal digit, 0 through 9, its own fixed 4-bit binary pattern, rather than converting an entire number into one large binary value.

BCD makes it simple to convert digits to and from binary one at a time, which mattered when circuits were built from simple hardware. But it only covers ten symbols. It has no way to represent a letter, a punctuation mark, or even a space.

From digits to a full alphabet: ASCII

As computers took on text — names, documents, commands — engineers needed a code that covered far more than ten digits. In the early 1960s, that need led to ASCII (American Standard Code for Information Interchange): the same underlying idea as BCD, a fixed-length binary pattern for every symbol, extended to cover uppercase and lowercase letters, punctuation, digits, and control characters, all inside a single 7-bit code.

A 7-bit code has 128 possible patterns, plenty of room for a whole keyboard's worth of symbols. But notice what it doesn't have: any built-in way to check whether a pattern arrived correctly. If a bit flips in transit, the result is just a different, equally valid character. That's the same silent-error problem from the drink-order code, wearing a bigger costume.

One common fix is to add a single check bit to every character, the same trick that turned our two-bit drink code into a detecting three-bit code. Here's what that looks like across a full alphabet.

This tells the receiver that something is wrong, but not what the original letter was. And not every error gets caught: if exactly two bits flip, the count of 1s stays even, and a damaged signal can slip through looking perfectly valid. Detecting an error and correcting one turn out to be two different problems.

Building a code that can fix itself

In 1950, mathematician Richard Hamming, frustrated with a computer that stopped and demanded a human's help every time it found an error, designed a code that could recover the original message on its own. The trick is redundancy, arranged carefully: every valid signal is built so that it differs from every other valid signal in at least three positions.

Because of that spacing, a single flipped bit moves a signal only one step away from where it started, but never closer than two steps to any other valid signal. That gap is what lets the receiver work backward and recover the original with confidence.

If more than one bit changes, the guarantee breaks down: the signal can drift close enough to a different letter to fool the receiver. Real systems handle that by adding still more redundancy, but the core idea stays the same. Spread valid signals far enough apart, and small errors become fixable instead of just noticeable.

The same ideas show up everywhere: add redundancy, space valid signals apart, check what arrives. QR codes, CDs and DVDs, computer memory, and deep-space communication all lean on some version of it. Every one of them is answering the question this page started with — if a bit gets flipped, how would you ever know?
