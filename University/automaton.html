1 · What is a finite automaton?

An automaton is an imaginary machine that is deliberately as simple as possible: it reads an input one symbol at a time, and the only thing it remembers is which state it is currently in. There is no scratch paper, no counter, no memory of what it read three symbols ago — unless that fact is baked into the state it moved to.

The job of a DFA: answer one yes/no question

A deterministic finite automaton (DFA) is a machine that decides a question about strings. You hand it a string; it reads the string left to right and finally says accept (yes, this string has the property) or reject (no, it does not).

Think of a bouncer with a very short memory, checking a rule like “does this string end with a 1?” or “does this string contain 01 somewhere?”. The bouncer cannot remember the whole string — only a small fixed set of facts, one per state. The art of building a DFA is choosing what each state should remember.

Vocabulary (we will use these words constantly)

  • Symbol — one character the machine can read. Ours are 0 and 1.
  • Alphabet (Σ, “sigma”) — the finite set of allowed symbols. On this page Σ = {0, 1} everywhere.
  • String — a finite sequence of symbols, e.g. 1001. The empty string is written ε (“epsilon”) and has length 0. It is a perfectly legal input!
  • Language — a set of strings. “All strings ending in 1” is a language. A DFA’s whole purpose is to define one.
  • Σ* — the set of all strings over Σ, including ε. A language is always some subset of Σ*.

The formal definition

A DFA is written as a 5-tuple — five pieces of data that together pin the machine down completely:

M = (Q, Σ, δ, q0, F)

The five parts
QA finite set of states. Finite is the whole point: the machine has a fixed, bounded memory.
ΣThe input alphabet, a finite set of symbols. Here always {0,1}.
δThe transition function δ : Q × Σ → Q. Given a state and a symbol, it names the next state. It is a function, so it gives exactly one answer for every input pair.
q0The start state, an element of Q. Exactly one, and the machine is in it before reading anything.
FThe set of accept states (also called final states), a subset of Q. Ending in one of these means “yes”.

Read δ out loud. δ(q1, 0) = q2 is read “from state q1, reading a 0, go to state q2”.

F may be empty, or all of Q. If F = ∅ the machine accepts nothing — its language is the empty set ∅. If F = Q it accepts everything — its language is all of Σ*. Both are legal DFAs. (Note: ∅ and {ε} are different languages — one contains no strings at all, the other contains exactly one string, the empty one.)

What makes it deterministic?

“Deterministic” means there is never a choice and never a dead end: from any state, reading any symbol, the machine’s next move is completely determined. Formally, three requirements:

  1. Exactly one start state. Not zero, not two.
  2. Exactly one transition out of every state for every symbol. With Σ = {0,1}, every state needs an arrow for 0 and an arrow for 1 — no missing transitions, no two arrows with the same label leaving the same state. (This is just another way of saying δ is a total function.)
  3. No ε-transitions. The machine may not change state “for free” without consuming a symbol. Every move eats exactly one input symbol.

Drop any of these and you get a nondeterministic finite automaton (NFA) — a useful machine, but a different one, and the subject of a later lecture.

A consequence of rule 2 that surprises people: if you want a DFA to “give up”, you cannot simply omit the arrow. You must send it to a trap state (also called a dead state) — a non-accepting state whose arrows all loop back to itself. You will build one in Exercise 3.

How a DFA computes

The whole procedure, with no cleverness at all:

  1. Start in q0 with the read head at the leftmost symbol.
  2. Read the current symbol a; move to state δ(current, a); advance one symbol.
  3. Repeat until the input is used up.
  4. If the state you land in is in F, accept; otherwise reject.

Notice that the machine always halts, after exactly |w| steps for an input of length |w|. It cannot loop forever, and it cannot stop early — it must consume the whole string. A DFA in an accept state half-way through has not accepted anything; only the state at the very end counts.

The empty string. Running ε means taking zero steps, so the machine is still in q0 when the input runs out. Therefore ε is accepted exactly when the start state is an accept state. That single fact settles a surprising number of exercises.

The language of a machine. We write L(M) = { w ∈ Σ* : M accepts w } — the set of all strings the machine says yes to. Two different-looking machines can have the same language; when they do, we call them equivalent. (The “Check my answer” button in section 4 is exactly an equivalence test.)

Three ways to write down the same machine

Reading a state diagram

  • A circle is a state, labelled with its name.
  • A double circle is an accept state. (The table also spells out “accept”, so you never have to rely on spotting the extra ring.)
  • An arrow coming from nowhere, labelled start, points at the start state.
  • A labelled arrow from p to q with label a means δ(p, a) = q.
  • An arrow can carry several labels: 0, 1 on one arrow is shorthand for two transitions that happen to have the same destination.
  • An arrow from a state back to itself (a self-loop) means “stay put, and remember nothing new”.

Reading a transition table

  • One row per state, one column per symbol; the cell holds δ(state, symbol).
  • → marks the start state; * marks accept states.
  • The table is the safest of the three notations: a missing cell is impossible to overlook, whereas a missing arrow in a diagram is easy to miss.

3 · Where these things actually live

Finite automata are not only a blackboard exercise. Any system with a small number of situations, driven by a stream of events, is a finite automaton — whether or not its author knew the word. Here are three you can poke at, and a list of others.

Demo 1 · A turnstile

The classic. Two states — Locked and Unlocked — and two events: insert a coin, or push the arm. We encode the events as our alphabet: 0 = coin, 1 = push. (Σ can be any finite set of symbols; calling them 0 and 1 is just a naming choice.)

Press the buttons and watch the state move. In a control application like this, the interesting output is the state itself, not an accept/reject verdict — but if we do declare F = {Unlocked}, then L(M) is exactly the set of event sequences that leave the gate open.

Demo 2 · Input validation: is this a well-formed binary numeral?

Every compiler and every form validator contains code shaped like this. Our rule: a binary numeral is either the single digit 0, or a string of digits that starts with 1. So 0, 1, 1011 are fine; 00, 011, and the empty string are not (no leading zeros, no empty literal).

Type and watch the verdict update on every keystroke, with the path through the machine shown live. This machine needs a trap state: once a leading zero is followed by anything, no later input can rescue the string.

Demo 3 · Text search: finding every occurrence of 0110

Search tools and regex engines compile a pattern into an automaton once, then scan the text in a single left-to-right pass, never backing up. The machine below remembers how much of the pattern has just matched: state k means “the last k symbols are the first k symbols of 0110, and no longer prefix matches”. Reaching state 4 means a match just ended here.

Notice what happens after a failed partial match — e.g. in 010110. The machine never re-reads a symbol; it just falls back to the longest prefix that is still alive. That is the Knuth–Morris–Pratt idea, and it is why this scan is linear time.

More of the same idea

Vending machine

States track the amount deposited so far (0¢, 25¢, 50¢…). Coins are the input symbols; the “dispense” state is the accept state. Finite because the machine only needs to count up to the price.

Traffic lights

Green → Yellow → Red → Green is a three-state automaton driven by timer ticks and sensor events. Pedestrian buttons add inputs, not memory.

Lexical analysis

The first phase of every compiler chops source text into tokens (identifiers, numbers, operators) using one big DFA, usually generated automatically from regular expressions by tools like lex/flex.

Regular expressions

Every regex without back-references denotes a language a DFA can decide — that is Kleene’s theorem. Fast engines (RE2, grep) really do build automata.

Network protocols

TCP’s connection lifecycle (LISTEN, SYN-SENT, ESTABLISHED, FIN-WAIT-1…) is specified as a state machine, and drawn as one in RFC 793.

UI and game logic

“Idle → Walking → Jumping → Falling”, or a dialog box’s enabled/disabled states. Modelling these as an explicit automaton is what stops the bug where two flags contradict each other.

The honest limitation

A DFA has finitely many states, and that is a real ceiling: a DFA cannot count without bound. No DFA accepts the language { 0n1n : n ≥ 0 } (01, 0011, 000111, …). The intuition: after reading the 0s the machine must remember exactly how many it saw, but with k states it can only distinguish k different counts, so two different prefixes 0i and 0j must land in the same state — and then the machine gives the same answer to 0i1i and 0j1i, one of which it should reject. Balanced parentheses and “palindromes” fail for the same reason.

That argument, made precise, is the pumping lemma. And the languages that are within reach have a name: the regular languages. Coming next in your course: NFAs (allow choice and ε-moves — surprisingly, no extra power), regular expressions (the same class again, in text form), and pushdown automata (add a stack, and 0n1n becomes easy).
